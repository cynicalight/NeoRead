# PDF 页面读图工具

> 当前由 Pi worker 通过工具桥接向 Go 请求页面图片。下文保留早期 Codex MCP 与 API 路径的实现和验证记录。参见[内置 Pi 与模型连接](../agent-streaming-contract.md#内置-pi-与模型连接)。

`read_pdf_pages({"pages":[3,5,6]})` 将当前 PDF 的指定页面渲染为图片，一次可请求最多八页，按请求顺序返回并去重。仅按需执行；普通文字仍使用 `read_passage`。原文没有可提取文字的扫描页也可以查看，不要求先完成翻译或版面模型分析。

渲染复用现有 PDF.js 和 Canvas，与版面分析共用页面渲染函数。采用白色背景、原生页面旋转、最多二倍缩放及约四百万像素/页。页面图片按文档原文版本缓存，重复读取复用缓存；文档删除时随文档缓存清理。模型只接受页码，不能指定文件路径、URL 或其他文档。

工具活动显示实际页码，如“正在查看第 3、5、6 页图像 · 核对图表、公式与版面”。返回每页尺寸、页码、来源 ID、原文版本与图片哈希。引用沿用现有来源展示与跳转，图片哈希和原文版本单独校验；图片页数与文字段落覆盖分别统计。

Codex 继续使用同一个原生线程；NeoRead MCP 返回文字页标记与 `image/png` 内容块。没有额外的描述图片或成文调用。API 只向同时具备工具能力与图片能力的当前聊天模型开放第四个工具；未验证或纯文本模型继续使用原有三个文字工具。新增可选图片工具不会使已有文字工具检测失效。

Chat Completions 的工具结果保持文字 JSON。完成这一组所有工具调用结果后，再追加包含页标记和 `image_url` 的多模态资料消息；这条消息与对应的调用/结果作为一个整体参与 compact，不当作新用户问题。SQLite 保存图片引用和证据元数据，请求上游时才从本地缓存加载图片，不把 base64 存进聊天或审计记录。

API 估算图片上下文时单独预留每页 8192 tokens，这只是保守预算，不代表实际计费。上下文不足时返回可继续读取的 `remainingPages`。单页最多 8 MiB、单组图片及单次 API 图片载荷最多 32 MiB；旧图片造成窗口或载荷增长时，旧工具组可以整体压缩。压缩只使用旧文字交互和图片来源元数据，不能重新获得已经从窗口移出的视觉细节，模型需要时应再次调用工具。新返回、尚未供模型查看的图片组不会提前压缩掉。

验证覆盖多页排序与去重、越界与能力限制、MCP PNG 内容、API 多模态接续、跨问题图片引用恢复、compact 分组、图片哈希校验、删除清理和实际 PDF.js 渲染。打包脚本包含独立渲染 worker，离线 smoke 检查指定页面输出。真实 Codex 验证使用仅含矢量图形的两页原创 PDF，确保图形数量不能从提取文字中获得；真实 API 视觉验证取决于用户已配置的多模态聊天模型，模拟协议通过不能替代它。

本次实际验证：Codex 一次工具调用返回两页，正确报告两个红色三角形和三个蓝色圆形，并通过两页引用校验；NeoRead 重启后继续回答和引用成功。typecheck、全包 Go 测试、前端 612 项测试（4 项跳过）、完整构建及相关 race 检查通过；Electron 内置 Node 下，阻断网络的处理器 smoke 通过，含旧版面解析和新增指定页渲染。尚未重新制作和验收完整安装包。

2026-10-15 后续修复：真实问答记录显示，旧 API 配置没有工具检测结果，导致只走 `retrieval`；自动聊天选择的 `deepseek-v4-pro` 也未通过图片检测。首次文档问答现会补做缺失的工具检测并缓存结果，提示词明确当前真实工具范围。经用户选择切换至 `deepseek-flash`；使用自然问题“第二页的图讲的是什么”，分别在原创图形和 Pictionary 论文副本上验证，模型主动调用 `read_pdf_pages`。论文验证实际读取第 2 页图像，来源 S264，并流式返回思考内容，无需在问题里指定工具名。大图请求另修正为多模态载荷边界，不再套用 4 MiB 纯文本请求上限。

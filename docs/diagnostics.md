# 本地日志与诊断包

NeoRead 持续保存本地运行日志。用户在「设置 → 诊断 → 导出全部日志」或原生「帮助 → 导出诊断包」选择保存位置，生成 ZIP 后自行发送给开发者。没有自动上传。

桌面版的代理设置和 ChatGPT 连接检测也在「设置 → 诊断」中，可先排查连接，再按需导出日志。检测固定访问 `https://chatgpt.com/robots.txt`；跟随系统模式检测当前已生效配置，切换系统代理后需重启 NeoRead。

## 导出范围

导出当前保留的全部 NeoRead 运行日志，包括正常、警告和错误事件、轮转文件以及之前的应用会话。不是仅提取错误或故障前后的时间窗口。功能上线前没有记录的历史和已经被保留策略删除的文件不能恢复。

桌面运行日志在应用 `userData/logs` 下；正式版与 `NeoRead Dev` 的路径分开。Go 服务通过 `--logs` 和 `--session` 使用同一目录与会话 ID，每个进程写独立文件。独立服务默认使用 `<library>/logs`。日志单文件约 5 MiB，运行日志按最后修改时间最多保留 7 天、目录总量约 100 MiB；启动和轮转时以及运行中定期清理最旧文件。

原有 `<library>/cache/<documentId>/translation-failures/*.txt` 也纳入导出。它们继续遵循原有每份文档最多 10 个文件的保留策略，不在运行日志目录的 100 MiB 限额内。导出不修改或删除这些源文件。

ZIP 包含：

- `logs/`：桌面生命周期、Go 请求及后台任务、AI 调用阶段、前端 API 和异常、服务标准错误。
- `legacy/translation-failures/`：已有翻译失败诊断，移除原始模型输出，新文件保留段落 ID、失败原因和全部尝试的解析统计。旧的交错格式在首次正文标记后全部移除，因此旧文件后续尝试的统计也会一并隐藏，避免模型伪造分隔符泄漏正文。
- `environment.json`：应用版本、构建提交、操作系统和架构、桌面运行时与时区；服务启动日志含 Go 版本。
- `settings.json`：白名单中的阅读/界面设置、主 Provider、聊天和翻译模型。桌面主进程缓存这些信息，服务退出后仍可导出。
- `manifest.json`：格式版本、导出时间、文件列表与修改时间、缺失/跳过的文件、日志写入失败次数、保留与脱敏规则。
- `README.txt`：供用户反馈时填写发生时间、操作步骤、预期和实际结果的提示。

日志按时间及 `sessionId`、`requestId`、后台 `taskId`、模型调用 `attemptId` 关联。HTTP 响应头 `X-NeoRead-Request-ID` 连接前后端；不改变聊天 SSE 事件和完成保存语义。日志记录阶段与结果，不记录滚动、鼠标移动或每个生成片段。

## 脱敏与边界

新日志不附带请求/响应正文、文档正文、聊天、批注、附件、剪贴板或环境变量全集。HTTP 失败只记录状态、稳定错误码和请求关联 ID，用户可见错误文案仍返回界面，但不落入日志，因为文案可能包含论文标题或裸主机名。导出同时移除旧日志中的 `userMessage` 字段；被截断的旧记录也不会保留该字段后的动态文案。前端异常记录异常类型和调用栈，丢弃可能含任意内容的异常消息首行。

采集和导出均处理结构化凭据字段、已知会话凭据、Bearer/Basic 认证、常见密钥和 JWT、URL、用户目录与 Windows 路径。URL 整体替换，避免查询参数、用户名或路径内携带凭据。旧翻译诊断的原始模型正文整体移除。原文件不变，ZIP 仅收集固定日志目录和固定翻译诊断路径，不递归打包书库、不读取 CLI 凭据文件，不包含 SQLite、PDF/EPUB、聊天或批注数据。

只接受固定字段、有限长度的渲染进程事件；IPC 校验主窗口和主 frame，浏览器模式 API 使用现有本地认证。符号链接、非普通文件和超过 32 MiB 的异常日志文件被跳过并记入清单，避免把其他文件或无界内容带入包。文件在导出时按快照长度读取，ZIP 逐文件压缩，不将所有日志同时装入内存。

脱敏针对 NeoRead 的日志字段及上述规则，不是对任意未知文本的保密证明。添加日志时必须遵守不采集正文和凭据的约定，不能依赖导出正则补救任意原始数据转储。

## 日志开发规范

涉及后台任务、外部调用、解析与协议、持久化、重试或恢复的变更，应按本节评估现有日志能否定位受影响流程的失败。有诊断缺口时补充安全的结构化事件；新增功能和修复 bug 都按此原则处理，已有日志充分时无需新增埋点。纯样式、间距、图标等不改变行为的调整无需新增日志。

本节的详细字段供按需参考，不要求为满足清单而改造本次范围之外的历史流程，也不表示所有历史模块已实现下述事件或字段。采集与导出的隐私边界、日志失败不影响业务的要求始终适用。

### 接入与关联

1. 检查受影响的入口、阶段、重要分支和保存边界，确认公共层已有记录能否说明失败原因。HTTP 中间件和 API client 已有请求日志；业务代码捕获的异常若缺少诊断信息，再在相应边界补充，未捕获异常监听无法覆盖此类异常。
2. 复用现有日志入口：Go 使用 `Server.diagnosticEvent` 或接入诊断 Store 的 `slog`，API 适配使用 `apiLog`；渲染进程使用 `reportDiagnostic`，桌面主进程使用诊断服务的 `record` / `logs.record`。新代码使用稳定事件名和结构化字段，不另建原始文本日志或直接转储任意对象。
3. 按实际链路复用 `sessionId`、HTTP `requestId`、后台 `taskId`、模型调用 `attemptId` 或解析 `runId`，保留必要的父子关联；每个操作无需具备全部 ID。一次业务操作包含多个任务或尝试时，应能从入口追到具体失败；后台任务脱离 HTTP 生命周期后仍需保留起源关联，独立任务则生成自己的任务 ID。关联 ID 不替代各自的取消和超时控制。
4. `DiagnosticEvent`、`validateDiagnosticEvent`、桌面 IPC 和 `POST /api/diagnostics/events` 有字段白名单与长度限制。新增渲染进程字段时，同步更新共享类型、两条接收路径的校验、脱敏和测试。下文的业务字段按需要接入，不是现有前端事件可以直接附带的字段全集；禁止把额外数据序列化进 `detail` 绕过白名单。

### 关键流程与按需字段

按本次变更涉及的边界参考下表，选择能区分故障的必要字段，无需为每个功能实现所有行或补齐全部字段。已有公共事件足以说明的步骤不重复记录；高频循环按阶段或批次汇总。

| 导入、解析与后台任务   | 开始、阶段切换、终态、阶段耗时、处理/失败数量；区分空文字页、未处理页和解析失败。原生进程可能在返回前退出的阶段，先写入阶段事件；PDF 的具体字段见下文。                                                                                |

| 重试、降级、缓存与恢复 | 触发原因、尝试序号、上限、退避时间、是否已产生可见输出；缓存命中/失效或跳过处理的原因。取消等待、停止重试和恢复后的结果也要有终态。                                                                                                    |

### 事件、原因与终态

- 事件名使用稳定的小写标识，如 `translation.stream_rejected`；遵循现有 `^[a-z][a-z0-9_.-]{0,79}$` 约定，不在事件名中插入文档 ID、路径或动态错误文案。
- 每个长操作记录开始和一个业务终态，并记录 `durationMs`；终态明确区分成功、失败和取消，需要重启恢复的任务另行表达暂停或中断。同层终态由一个位置负责，避免多层 catch 为同一次失败重复收尾。进程崩溃可能只留下开始或阶段记录，此时结论是终态未知，不能补造成功或失败。
- `errorCode` 表达稳定错误大类，如 `protocol`、`timeout`、`save`；必要时用受控 `reasonCode` 和 `phase` 细分，如 `unsupported_status`、`config_field_type_mismatch`、`unknown_citation_source`、`corpus_revision_changed`。用户提示仍可保持简洁，诊断字段应能区分不同触发点，不能只剩 `Error` 或一条通用“未完成”。
- 日志级别按事件所描述的结果选择：正常阶段、成功、用户主动取消为 `info`；因异常决定继续有限重试或降级的决策事件为 `warn`；单次尝试或业务操作的失败终态为 `error`，包括导致该层失败的协议校验或保存错误。失败尝试后来重试成功时，业务最终事件为 `info`。预期的空文字页或无需处理项记录为正常结果，不作为故障。
- 区分 HTTP 响应建立、Provider 完成、内容校验通过和业务保存成功。HTTP 200、已有文字或模型返回成功都不能替代保存终态；用明确阶段说明耗时的起止，API client 收到响应头的耗时不能当作完整 SSE 耗时。

例如，译文快照因未知状态值而被拒绝时，应能留下类似下面的安全校验摘要。这是待按规范接入的事件示例，不表示当前已自动生成：

```json
{
  "event": "translation.stream_rejected",
  "level": "error",
  "requestId": "example-request-id",
  "phase": "snapshot_validation",
  "errorCode": "protocol",
  "reasonCode": "unsupported_status",
  "field": "status",
  "actualState": "unrecognized"
}
```

`actualState: "unrecognized"` 表示收到的未知状态值已归一化，不保存原始字符串。合法的 `idle` 表示尚未请求翻译的段落，必须正常接受，不触发该拒绝事件。

它能指向前后端状态约定；仅记录“译文事件格式无效”无法区分状态不兼容、字段缺失和 JSON 解码失败。`field` 应来自受控 schema；用户定义的动态键名统一归一化。编号、数量、布尔值和修订标识按诊断需要记录，配置仅记录变更标识或是否匹配，不单独散列或记录凭据。

### 隐私、完整性与验证

沿用上文的采集与导出边界。原始异常消息、CLI 配置、工具参数/结果、模型输出和文档内容不能作为通用诊断附件；用白名单原因、类型和计数替代。需要指纹时采用现有受限实现，并说明它只用于比对，不能作为内容或根因证明。可能产生大量重复事件的高频路径应聚合或限频，同时保留首次原因、累计次数及最终结果；低频有限重试可逐次记录。日志写入失败不得影响阅读、保存、流式完成和取消语义，也不得递归上报日志失败。

提交前只检查本次适用项，复用已有验证覆盖；无需为每个功能新增一套日志专项测试：

- [ ] 仅改业务逻辑且已有日志足够：执行相关业务验证即可，无需新增埋点或诊断测试。
- [ ] 新增或修改关键业务事件：通过相关回归测试或最小复现验证受影响的正常路径和关键失败/取消路径，确认必要的阶段、原因及关联能区分故障、说明结果是否保存。复用已有测试，必要时补充稳定字段断言，不快照整份动态日志。
- [ ] 修改日志传输、字段白名单、脱敏、落盘或导出：针对受影响边界运行或补充诊断回归，验证相应的字段/长度限制、写入失败、故障时导出或缺失报告。涉及采集或脱敏规则变化时，使用可识别的正文/凭据标记验证落盘及导出均不泄漏。
- [ ] 涉及诊断变更时，在变更说明中交代埋点、验证结果及仍需样本或复现的限制；纯文档修改只需内容、链接与差异检查。

排查未找到事件的情况时，先核对实例、版本、会话、时间范围和 `manifest.json` 的缺失报告，不据此断言操作未执行。

## 故障时导出

- React 渲染错误的备用界面保留「导出全部日志」按钮。
- 服务异常退出、渲染进程崩溃或启动失败时，原生提示提供「导出诊断包」，可导出后退出。
- 原生帮助菜单与 Electron 导出逻辑独立于 React 和 Go 服务；桌面导出不调用服务，也不打开书库数据库。
- 桌面主进程完全崩溃时，重新启动后可导出此前已经写入磁盘的日志。磁盘不可写时只保留有限内存尾部，并在清单报告丢失写入。
- 浏览器开发模式通过认证的 `POST /api/diagnostics/events` 记录前端事件，通过 `GET /api/diagnostics/export` 下载服务能访问的日志；浏览器没有桌面进程，服务停止后需要恢复服务才能读取磁盘日志。

无法读取或在导出过程中消失的日志会在清单中注明。桌面包存在缺失或写入失败时显示提示。文件写入失败不应阻止阅读、保存或已有 API 返回；取消系统保存对话框不生成诊断包。

日志能缩小问题范围，但依赖特定文件内容的解析/渲染问题可能仍需要用户另行提供样本。

## 手动验收

1. 在独立开发书库中启动桌面版，导入样本并打开、切换主题；从设置导出，检查 ZIP 含正常事件和运行环境，且没有文档或数据库。
2. 退出并重启，再导出，检查两次会话均在日志中。
3. 让开发环境服务异常停止，使用原生故障提示导出；确认不需要服务恢复。
4. 使用开发者工具触发未捕获异常，检查前端异常日志；React 错误备用界面和渲染进程崩溃路径由回归测试覆盖，人工检查原生帮助菜单仍可导出。
5. 取消保存，检查没有残留目标 ZIP；保存到不可写位置时应提示失败，可重新选择位置。

自动测试覆盖脱敏、跨会话/级别导出、旧翻译诊断、ZIP CRC、轮转和过期清理、符号链接边界、IPC frame 校验、离线桌面导出、React 错误界面以及 HTTP ResponseController Flush 兼容。全项目检查仍要求 `pnpm typecheck`、`pnpm test`、`pnpm build`。视觉验收采用人工检查。

## API 适配诊断

API 厂商规则、实际强度映射、上游错误分类和请求关联字段见 [API 厂商适配与错误诊断](api-provider-compatibility.md)。新增 API 错误事件只记录安全的结构化证据，不保存厂商可能回显正文的原始错误 message。

## PDF 本地解析诊断

`pdf.parse.start / spawned / stage / finish` 使用 `runId` 和 `documentId` 关联一次解析。记录原生 Canvas、ONNX Runtime 加载、PDF.js 加载、输出目录准备、模型校验、CPU 推理会话创建、PDF 读取与打开、逐页渲染/推理/文本提取、附件与清单写入等阶段。`stage` 是正在执行的阶段；后续阶段出现表示前一阶段已返回。失败时记录白名单异常类型和系统错误码、异常指纹，最终事件记录退出码、耗时、取消状态，以及标准错误的字节数、有限尾部指纹和截断标记。

不保存原始异常消息、调用栈或子进程标准错误正文，它们可能含 PDF 正文、文件名和用户路径。即使原生进程直接崩溃，Go 仍记录最后收到的阶段和退出码；尚未进入 JavaScript 时，最后阶段为 `bootstrap`。`exitCode=-1` 表示没有正常退出码（例如未启动或被信号终止），应结合阶段判断。`timeout` 表示解析子进程达到时间上限。

用户安装包含此改动的版本后，对同一 PDF 点击重试，等待成功或失败再导出诊断包即可。无需开启调试模式或提供书库数据库。新增日志用于定位故障，不代表已修复原有解析问题。

### 原生初始化崩溃的补充证据

阶段事件同步写入子进程管道，避免原生代码突然退出时丢失缓冲区内的最后阶段。每个阶段记录 Node/Electron 版本、进程 RSS、JS 堆与外部内存、系统可用及总内存；`session_create` 额外记录 ONNX Runtime 版本。系统可用内存是采样值，不能单独证明或排除内存不足。

开启 ONNX 初始化详细输出后，Go 在内存中按固定特征提取 `nativeDiagnostics`：线程池创建、会话初始化、图优化、张量初始化、初始化完成，以及 Crashpad 未连接、分配失败、Node 致命错误等。只导出固定分类码，不保存原始行；未知消息仍仅保留字节数与尾部指纹。分类跨管道分片且保留早期特征，内存使用有上限。分类码表示观察到的消息，不能替代原生崩溃栈或作为单独的根因证明。

最终事件的 `nativeTrace` 额外保留最近 32 个白名单原生源码文件名与行号（例如 `inference_session.cc:534`），不含本机路径和原始消息。它用于对照原生库源码缩小初始化内部的失败范围。

最终事件增加 `exitCodeHex`。Windows 的 `0xFFFF7003` 对应 Crashpad 未连接到崩溃处理程序，不能据此判断最初的异常原因。本次补充不会恢复旧诊断包中已丢弃的 stderr，也不保证所有原生崩溃均可仅凭日志确诊。

## 联网搜索配置与权限

`web.search.config_saved / config_rejected` 记录保存结果、CLI 是否启用、搜索服务类型和是否配置密钥；`web.search.permissions` 记录一次提问请求的提供方、请求的联网状态及设置核验后的授权结果，均带 `requestId`。不采集搜索服务地址、任何 Key、搜索词、网页内容或问题正文。

## PDF 显示渲染

译文 PDF 导出记录 `pdf.translation_export.start / stage / failed / cancelled / download_requested`，用 `requestId` 关联一次导出。阶段为读取快照、排版、保存、请求下载；结果只记录页数、已替换段落数和保留区域数，不记录文件名、正文或异常原文。`download_requested` 表示浏览器已接收下载请求，不代表已经完成磁盘写入。导出取消或失败不修改原文和译文。 失败终态通过 `detail` 中的 `errorCode` 和 `reasonCode` 记录受控分类，区分快照读取、字体下载、模块加载、PDF 解码、加密 PDF、字体嵌入、页面尺寸、排版、无可导出段落、保存、资源清理和下载失败；未知异常使用当前操作的分类或 `unrecognized`，不将异常名称、正文或堆栈写入日志。取消使用 `reasonCode=user_cancelled`，保持 info 级别。

`pdf.render.failed` 记录阅读实例首次页面或局部高清渲染失败，`detail` 只包含固定的 `pipeline=object-colors/original` 和 `layer=page/detail`。不记录原始异常、文档文本或路径。每个实例最多一次，避免持续失败造成日志洪泛。对象级配色、画布替换与人工验收范围见 [PDF 对象级配色](pdf-object-colors.md)。
